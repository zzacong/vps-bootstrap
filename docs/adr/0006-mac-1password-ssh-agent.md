# 0006-mac-1password-ssh-agent

Supersedes [0002-mac-host-key-keychain-policy](./0002-mac-host-key-keychain-policy.md). The Mac flow generates no SSH key: the operator's 1Password key is the only GitHub credential, exactly as in the VPS flow (ADR-0005). `setup-mac.sh` links `~/.1password/agent.sock` to the agent socket in 1Password's group container, writes `~/.ssh/config` with `IdentityAgent ~/.1password/agent.sock`, and verifies that `ssh -T git@github.com` answers before the `yadm` clone. No passphrase is prompted for, no key is written to `~/.ssh`, and no Keychain item is created.

ADR-0002 stored a passphrase in the Keychain for a key generated on the Mac. That key existed to authenticate the dotfiles clone and later GitHub work, and the 1Password key already covers both. Keeping it meant the Mac flow carried the bootstrap's heaviest machinery (an SSH_ASKPASS helper, two passphrase prompts, a script-local agent, a Keychain item) for a credential the operator no longer uses, and it left a long-lived private key on disk where the VPS flow deliberately keeps none. Dropping it makes both flows say one thing: 1Password holds the key.

The trade-off is a manual prerequisite the script cannot install. 1Password must be installed and signed in with Developer → SSH agent enabled, holding a key whose public half is on the GitHub account that owns the dotfiles. The script fails with that checklist when the app's group container is absent, and the pre-clone `ssh -T` probe fails with it when GitHub refuses the agent. macOS points `SSH_AUTH_SOCK` at its own agent rather than 1Password's, so `~/.ssh/config` must carry the `IdentityAgent` line. That file is not in the dotfiles repo (the clone is what needs it), so the script writes it when absent and leaves an existing file alone, only warning when it names no `IdentityAgent`.
