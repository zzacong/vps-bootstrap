# 0005-vps-1password-agent-forwarding

The VPS flow keeps no private keys on the server. One 1Password-managed key on the operator's host does both jobs the old flow split across two keys: its public half is pasted (via `ssh-add -L`) into the new user's `authorized_keys` for login, and the same key authenticates the VPS to GitHub through agent forwarding (`ssh -A` / `ForwardAgent yes`) for the `yadm` dotfiles clone. `setup-user.sh` asserts `$SSH_AUTH_SOCK` is set, `ssh-add -L` shows keys, and `ssh -T git@github.com` answers as the dotfiles repo owner (derived from the clone URL) before cloning — and it never starts a script-local ssh-agent, which would overwrite `$SSH_AUTH_SOCK` and hide the forwarded agent.

This supersedes ADR-0001 for the VPS flow. ADR-0001's discipline (required passphrase, confirmed twice, delivered via SSH_ASKPASS helper, never in argv) solved the least-safe aspect of the old scripts — a hardcoded deploy-key passphrase living on a server. Forwarding removes the problem instead of managing it: there is no server-side secret to protect, so there is no passphrase to prompt for, confirm, carry between steps, or feed through askpass plumbing, and no add-a-key-to-GitHub manual step (the 1Password public half is already there). The passphrase/askpass machinery remains only in the Mac flow (ADR-0002), where the key lives on the operator's own machine and the Keychain persists it.

The trade-off is a session dependency: step 3 fails fast without `ssh -A`, and with several keys in the agent GitHub answers as the first one it accepts — hence the repo-owner check turning a wrong-account win into a clear error instead of a confusing clone failure. Forwarding also exposes the agent for the session lifetime; acceptable here because 1Password gates each use behind its own auth, and bootstrap sessions are short-lived.
